## 摘 要

　　随着零售行业的快速发展，超市日常经营中涉及大量的商品采购、库存和销售管理工作。传统的人工记录方式效率低下、容易出错，已经无法满足现代超市的管理需求。本系统基于Spring Boot框架和Vue.js前端技术，采用MyBatis作为持久层框架，以MySQL作为数据库，设计并实现了一套超市进销存管理系统。

　　系统分为管理员和普通用户两种权限角色。管理员模块实现了供应商管理、商品管理、员工管理、会员管理和采购管理五大核心功能，支持数据的批量导入、增删改查操作。普通用户模块提供了个人信息查看、商品信息查询和采购信息查询功能。系统采用事务管理机制确保采购主表与明细表的数据一致性，通过外键约束保证数据完整性。本系统能够有效提高超市日常运营的管理效率，降低人工成本，为超市信息化建设提供有力支撑。

**关键词：超市进销存；Spring Boot；MyBatis；Vue.js；采购管理；事务管理**

## Abstract

With the rapid development of the retail industry, daily supermarket operations involve a large amount of commodity procurement, inventory, and sales management. Traditional manual recording methods are inefficient and prone to errors, and can no longer meet the management demands of modern supermarkets. This system is designed and implemented based on the Spring Boot framework and Vue.js front-end technology, using MyBatis as the persistence layer framework and MySQL as the database.

The system is divided into two permission roles: administrator and regular user. The administrator module implements five core functions including supplier management, goods management, employee management, member management, and purchase management, supporting batch data import and CRUD operations. The regular user module provides personal information viewing, goods information query, and purchase information query functions. The system adopts a transaction management mechanism to ensure data consistency between the purchase master table and detail table, and ensures data integrity through foreign key constraints. This system can effectively improve the management efficiency of daily supermarket operations, reduce labor costs, and provide strong support for supermarket informatization construction.

**Key Words:** Supermarket Purchase-Sales-Inventory; Spring Boot; MyBatis; Vue.js; Purchase Management; Transaction Management

## 1. 引言

### 1.1 系统背景

　　随着我国经济的持续发展和居民消费水平的不断提高，超市作为零售行业的重要组成部分，其经营规模不断扩大，商品种类日益丰富。然而，许多中小型超市在日常管理方面仍然依赖传统的手工记录或简单的电子表格，这种方式存在以下突出问题：

　　（1）数据录入效率低下。当超市商品种类繁多、供应商数量庞大时，手工记录的工作量急剧增加，容易出现遗漏和错误。

　　（2）信息查询不便。采购记录、商品信息、供应商资料等分散存储，难以快速检索和统计分析。

　　（3）数据一致性难以保证。采购过程中涉及采购主表和采购明细表，手工操作容易出现两张表数据不一致的情况。

　　（4）权限管理缺失。员工和管理员使用同一套系统时，无法有效区分操作权限，存在数据安全隐患。

　　基于上述背景，开发一套功能完善、操作简便的超市进销存管理系统具有重要的现实意义。

### 1.2 系统开发的意义

　　从业务层面来看，本系统能够帮助超市实现供应商信息、商品信息、员工信息、会员信息和采购信息的集中管理，提高数据录入和查询效率。管理员可以通过系统快速完成批量数据导入，普通员工能够方便地查询商品和采购信息，有效降低了日常管理的人力成本。

　　从技术层面来看，本系统采用Spring Boot + MyBatis的后端架构和Vue.js的前端框架，是当前企业级应用开发的主流技术方案。通过本系统的开发实践，能够深入理解前后端分离架构的设计思想，掌握RESTful API的设计规范，学习数据库设计和SQL优化技术，以及事务管理在实际业务中的应用。

## 2. 相关技术研究

### 2.1 Spring Boot

　　Spring Boot是由Pivotal团队提供的开源Java框架，旨在简化Spring应用的初始搭建和开发过程。其核心特点是"约定优于配置"，通过自动配置机制大幅减少了XML配置文件和手动配置的工作量。Spring Boot内嵌了Tomcat、Jetty等Web服务器，开发者无需部署WAR包即可直接运行应用。

　　在本系统中，Spring Boot作为后端核心框架，承担了以下职责：提供RESTful API接口服务；通过控制反转（IoC）容器管理Bean的生命周期和依赖关系；利用面向切面编程（AOP）实现事务管理；通过参数校验框架完成请求数据的自动验证。

### 2.2 Vue.js

　　Vue.js是一套用于构建用户界面的渐进式JavaScript框架，由尤雨溪于2014年发布。Vue.js采用自底向上的增量开发设计，核心库只关注视图层，易于上手，同时通过丰富的生态系统（如Vue Router、Vuex、Element UI等）支持复杂单页应用的开发。

　　Vue.js的核心特性包括：响应式数据绑定机制，当数据发生变化时视图自动更新；组件化开发模式，将页面拆分为独立可复用的组件；虚拟DOM技术，通过Diff算法高效更新真实DOM，提升页面渲染性能。本系统前端采用Vue.js配合Element UI组件库，构建界面美观、交互流畅的管理系统。

### 2.3 MyBatis

　　MyBatis是一款优秀的Java持久层框架，它通过XML或注解的方式将Java对象与SQL语句进行映射，实现了SQL与业务代码的分离。相比于Hibernate等全自动ORM框架，MyBatis更加灵活，开发者可以自主编写和优化SQL语句，更适合复杂查询场景。

　　在本系统中，MyBatis作为数据访问层框架，负责所有数据库操作。通过Mapper接口与XML映射文件的配合，实现了实体对象的增删改查操作。同时利用动态SQL功能（如`<if>`、`<foreach>`标签），实现了灵活的条件查询和批量操作。MyBatis的`map-underscore-to-camel-case`配置使得数据库下划线命名与Java驼峰命名自动转换，减少了大量手动映射工作。

### 2.4 Redis

　　Redis（Remote Dictionary Server）是一个开源的高性能键值对存储系统，通常用作数据库、缓存和消息中间件。Redis支持字符串、哈希、列表、集合、有序集合等多种数据结构，所有数据存储在内存中，读写性能极高（可达10万+ QPS）。Redis还支持数据持久化（RDB快照和AOF日志）、主从复制、哨兵模式和集群分片等高级特性。

　　在本系统中，Redis作为缓存层使用。通过Spring Cache抽象（`@Cacheable`、`@CacheEvict`注解），对频繁查询的单条记录（商品、员工、会员、供应商）进行缓存，有效降低数据库重复查询压力，提升接口响应速度。Spring Cache的自动失效机制保证了缓存数据与数据库的一致性，TTL过期策略防止了缓存雪崩。

## 3. 需求分析

　　本系统面向超市的日常进销存管理场景，设计了两类用户角色：管理员和普通用户。各角色的核心功能需求如下：

**管理员用户登录模块：**

· **供应商管理**：支持批量录入供应商数据，手动输入供应商编号、供应商名称、供应商简称、地址、公司电话、邮件、联系人、联系人电话、备注。支持查询并列出表中所有供应商信息。支持修改指定供应商的信息。支持删除指定供应商数据。

· **商品管理**：支持批量录入商品数据，手动输入商品编号、商品名称、商品单价、供应商编号、商品简介、备注等。支持查询并列出所有商品信息。支持修改指定商品的商品信息。支持删除指定商品数据。

· **员工管理**：支持批量录入员工数据，手动输入员工编号、员工姓名、员工密码、员工级别、员工电话、员工工资、备注等。支持查询并列出所有员工信息。支持修改指定员工信息。支持删除指定员工数据。**支持用户自行注册**，注册后需管理员审批通过（is_approved=1）方可登录。管理员可在"待审批"Tab中通过或拒绝注册申请。

· **会员管理**：支持对会员信息进行增删改查操作，包括会员姓名、电话、邮箱、积分、会员等级等信息的管理。

· **采购管理**：支持录入采购主表数据（采购清单号、员工编号、采购数量、采购总价、采购时间、备注）和采购明细数据（采购明细号、采购清单号、商品编号、采购数量、商品单价、商品总价、备注）。支持查询并列出所有采购主表和采购明细信息。支持修改和删除指定采购信息。

**普通用户登录模块：**

· **个人信息**：查询自己的员工信息。

· **商品信息**：查询所有商品信息。

· **采购信息**：查询所有的采购信息。

## 4. 总体设计

### 4.1 架构设计

　　本系统采用前后端分离的B/S架构模式，整体分为三层：表现层（前端Vue 3 + Element Plus应用）、业务逻辑层（Spring Boot后端服务）和数据访问层（MyBatis持久层）。前端通过HTTP协议发送JSON格式的请求到后端API接口，后端处理业务逻辑后操作MySQL数据库，并将结果以JSON格式返回给前端。系统核心设计原则包括：后端遵循Fail-fast校验、不信任前端传参、通过@Transactional保证多表操作原子性、三层防重复提交机制（前端5秒冷却+后端5秒限流+订单号防重）。

### 4.3 数据库设计

　　此次系统使用的数据库为MySQL数据库，对数据进行持久层的存储与处理，确保了数据的安全存储和持久性。经过综合设计与考虑，并针对实际需求的需要，设置了6个数据库表。其中核心模块包括：

　　（1）基础数据模块：包含供应商表（supplier）、商品表（goods）、员工表（employee）、会员表（member），构成系统的基础数据体系。

　　（2）采购业务模块：包含采购主表（purchase_main）和采购明细表（purchase_detail），实现采购业务的数据存储。

　　各表之间的关系如图4.3所示：供应商与商品是一对多关系（一个供应商可以提供多种商品）；员工与采购主表是一对多关系（一个员工可以创建多个采购单）；采购主表与采购明细是一对多关系（一个采购单包含多条采购明细）；商品与采购明细是一对多关系（一种商品可以出现在多条采购明细中）。

　　数据库整体ER图及外键删除策略如下：

```

│ supplier │       │ employee │       │     member     │
│ (供应商) │       │ (员工)   │       │    (会员)      │
└────┬─────┘       └────┬─────┘       └────────────────┘
     │                   │
     │ RESTRICT          │ RESTRICT
     ▼                   ▼
┌──────────┐       ┌────────────────┐
│  goods   │       │ purchase_main  │
│ (商品)   │       │   (采购主表)    │
└────┬─────┘       └───────┬────────┘
     │                     │
     │ RESTRICT            │ CASCADE
     │                     │
     └──────────┬──────────┘
                ▼
         ┌────────────────┐
         │purchase_detail │
         │  (采购明细)     │
         └────────────────┘
```

　　外键删除策略遵循以下原则：**CASCADE**用于组合关系（采购主表→明细，同生共死）；**RESTRICT**用于关联关系（供应商→商品、员工→采购主表、商品→明细，有引用时阻止删除，保护历史数据完整性）。六张表概览：supplier/goods/employee/member 使用逻辑删除（is_deleted），purchase_main/purchase_detail 使用物理删除（通过状态机管理生命周期）。

## 5. 系统实现

### 5.1 登录模块

　　登录模块是系统的入口，员工通过手机号和密码进行身份验证。系统使用SHA-256算法对密码进行哈希加密，与数据库中存储的密文进行比对。登录成功后，后端返回员工信息（不含密码字段），前端根据员工的level字段判断是管理员（level=2）还是普通员工（level=1），从而展示不同的功能菜单。

　　登录模块的核心代码逻辑如下：

```java
// EmployeeServiceImpl.java - 登录验证
public Employee login(String phone, String password) {
    // 根据手机号查询员工
    Employee employee = employeeMapper.selectByPhone(phone);
    if (employee == null) {
        throw new BusinessException("账号不存在");
    }
    // SHA-256加密后比对密码
    if (!PasswordUtil.matches(password, employee.getPassword())) {
        throw new BusinessException("密码错误");
    }
    // 检查审批状态
    if (employee.getIsApproved() != null && employee.getIsApproved() == 0) {
        throw new BusinessException("您的账号正在等待管理员审批");
    }
    // 清除密码后返回
    employee.setPassword(null);
    return employee;
}
```

### 5.4 员工管理模块

　　员工管理模块实现了员工信息的增删改查和批量导入功能。相比其他模块，员工模块的特别之处在于实现了**用户注册+管理员审批**机制，以及密码的加密存储策略。

#### 用户注册与审批机制

　　系统设计了完整的注册审批流程，包含三种状态和两条路径：

```
　　　　用户注册
　　　　　　↓
　　　　is_approved = 0 (待审批)
　　　　/　　　　　　\
　　 管理员通过　　  管理员拒绝
　　(is_approved=1)　(标记离职)
　　　　↓
　　 正常登录使用
```

　　用户通过 `POST /api/employee/register` 接口自行注册，注册时需提供姓名、手机号和密码。系统自动将 `level` 设为 1（普通员工），`is_approved` 设为 0（待审批），密码使用 SHA-256 加密后存储：

```java
// EmployeeServiceImpl.java - register()
public void register(Employee employee) {
    validateEmployee(employee);
    // 校验手机号唯一性
    Employee existing = employeeMapper.selectByPhone(employee.getPhone());
    if (existing != null) {
        throw BusinessException.duplicate("手机号已注册");
    }
    employee.setPassword(PasswordUtil.encode(employee.getPassword()));
    employee.setLevel(1);
    employee.setIsApproved(0);  // 待审批
    employeeMapper.insert(employee);
}
```

　　管理员通过 `GET /api/employee/pending` 接口获取所有待审批注册申请，在管理界面的"待审批"Tab 中以列表形式展示。管理员可对每条申请执行两种操作：

- **通过审批**（`PUT /api/employee/approve/{id}`）：将 `is_approved` 设为 1，员工可正常登录
- **拒绝申请**（`PUT /api/employee/reject/{id}`）：标记离职（`is_deleted=1`），与其他模块的软删除策略一致

```java
// EmployeeServiceImpl.java - approve() / reject()
public void approve(Integer id) {
    int rows = employeeMapper.approve(id);  // UPDATE is_approved = 1
    if (rows == 0) throw BusinessException.notFound("员工");
}

public void reject(Integer id) {
    int rows = employeeMapper.reject(id);   // UPDATE is_deleted = 1
    if (rows == 0) throw BusinessException.notFound("员工");
}
```

　　登录时系统会校验 `is_approved` 状态，未审批通过的用户将被拦截：

```java
// EmployeeServiceImpl.java - login()
if (employee.getIsApproved() != null && employee.getIsApproved() == 0) {
    throw new BusinessException("您的账号正在等待管理员审批");
}
```

#### 密码与权限

　　管理员直接新增员工时（`POST /api/employee/add`）自动将 `is_approved` 设为 1（无需审批），默认密码为 `"123456"`，使用 SHA-256 算法加密存储。员工通过 `level` 字段区分权限：普通员工（level=1）和管理员（level=2）。API 返回员工信息时自动清除密码字段，防止密码泄露。

#### 删除保护

　　删除员工前系统会检查该员工是否关联采购记录，存在记录时阻止删除并提示关联数量：

```java
int purchaseCount = employeeMapper.countPurchaseByEmployeeId(id);
if (purchaseCount > 0) {
    throw new BusinessException(
            String.format("该员工有%d条采购记录，无法删除", purchaseCount));
}
```

### 5.5 采购管理模块

　　采购管理模块是系统的核心业务模块，实现了采购单的创建、查询、修改、核实、作废和恢复功能。采购单采用状态机模型管理生命周期，包含三种状态：

- **DRAFT（草稿）**：创建后的初始状态，允许修改、作废，可被管理员核实提前截止
- **HISTORY（已截止）**：只读状态，不可修改。到达截止时间后自动进入此状态
- **CANCELLED（已作废）**：用户手动作废，或管理员拒绝后进入此状态，可恢复

　　状态转换规则如下：

```
                      用户提交采购
                           ↓
                     ┌─────────────┐
                     │    DRAFT    │  ← 可修改、核实、作废
                     │   (草稿)     │
                     └──────┬──────┘
                            │
              ┌─────────────┼─────────────┐
              │             │             │
           用户修改       用户作废    管理员核实 /
           重新提交          │        1小时后自动截止
              │             │        (@Scheduled 每分钟轮询)
              ▼             ▼             ▼
        回到 DRAFT    ┌──────────┐  ┌──────────┐
                      │CANCELLED │  │ HISTORY  │
                      │ (已作废)  │  │ (只读)    │
                      └────┬─────┘  └──────────┘
                           │
                     用户可恢复
                      (截止时间前)
```

#### 三层防重复提交机制

　　为防止重复提交，系统设计了三层防线：

- **第1层 — 前端按钮冷却**："创建采购单"按钮在弹窗关闭后进入 5 秒冷却，冷却期间点击无反应。通过 `setInterval`/`clearInterval` 实现倒计时展示，`onUnmounted` 生命周期清理定时器，确保组件卸载后不产生副作用。
- **第2层 — 后端限流**：后端使用 `ConcurrentHashMap<Integer, Long>` 记录每个员工最近一次提交的时间戳，5 秒内再次提交返回 429 并提示剩余等待时间。
- **第3层 — 订单号防重复**：前端先调用 `GET /api/purchase/pre-order` 获取预订单号，提交时后端校验该单号未被使用过。通过 `Map<String, Long>`（存储时间戳）记录，每次 generate/submit 时清理 30 分钟前的过期条目，防止内存泄漏。

　　采购价格从数据库 Goods 表实时获取，不信任前端传入的数据，杜绝篡改风险。

#### 采购提交流程（事务管理）

　　新增和修改采购单涉及主表和明细表两张表的数据写入，必须保证所有操作在同一事务中。系统采用 `@Transactional(rollbackFor = Exception.class)` 注解，任何步骤出现异常时自动回滚全部操作。提交流程的业务逻辑如下：

```java
// PurchaseServiceImpl.java - submit()
@Override
@Transactional(rollbackFor = Exception.class)
public Result<String> submit(PurchaseSubmitDTO dto) {
    // ========== Fail-fast 校验 ==========
    if (dto.getEmployeeId() == null)
        throw BusinessException.paramError("员工ID不能为空");
    if (dto.getDetails() == null || dto.getDetails().isEmpty())
        throw BusinessException.paramError("采购明细不能为空");

    // ========== 第2层：5秒限流 ==========
    Long lastTime = lastSubmitTime.get(dto.getEmployeeId());
    if (lastTime != null && System.currentTimeMillis() - lastTime < 5000) {
        long remain = 5 - (System.currentTimeMillis() - lastTime) / 1000;
        throw new BusinessException(429, "操作太频繁，请" + remain + "秒后重试");
    }

    // ========== 第3层：订单号防重复 ==========
    cleanupExpiredOrderNos();
    Long submitTime = usedOrderNos.get(dto.getPreOrderNo());
    if (submitTime == null)
        throw new BusinessException("订单号无效，请刷新页面重新提交");
    usedOrderNos.remove(dto.getPreOrderNo());

    // ========== 从数据库获取价格，计算总价 ==========
    List<PurchaseDetail> details = new ArrayList<>();
    BigDecimal totalPrice = BigDecimal.ZERO;
    int totalQuantity = 0;
    for (PurchaseSubmitDTO.DetailItem item : dto.getDetails()) {
        Goods goods = goodsMapper.selectById(item.getGoodsId());
        if (goods == null) throw BusinessException.notFound("商品");
        BigDecimal unitPrice = goods.getPrice();
        BigDecimal itemTotal = unitPrice.multiply(
                new BigDecimal(item.getQuantity()));
        // 构建采购明细对象...
        totalPrice = totalPrice.add(itemTotal);
        totalQuantity += item.getQuantity();
    }

    // ========== 检查今天是否已有DRAFT订单 ==========
    PurchaseMain existingDraft = mainMapper.selectTodayDraft(
            dto.getEmployeeId(), todayStart);
    if (existingDraft != null) {
        // 已有草稿 → UPDATE（更新主表 + 删除旧明细 + 插入新明细）
        existingDraft.setTotalQuantity(totalQuantity);
        existingDraft.setTotalPrice(totalPrice);
        mainMapper.update(existingDraft);
        detailMapper.deleteByMainId(existingDraft.getId());
        for (PurchaseDetail detail : details)
            detail.setPurchaseMainId(existingDraft.getId());
        detailMapper.batchInsert(details);
    } else {
        // 无草稿 → INSERT（创建主表 + 插入新明细）
        String orderNo = "PO-" + LocalDate.now()
                .format(DateTimeFormatter.ofPattern("yyyyMMdd")) + "-"
                + String.format("%05d", System.currentTimeMillis() % 100000);
        PurchaseMain main = new PurchaseMain();
        main.setOrderNo(orderNo);
        main.setEmployeeId(dto.getEmployeeId());
        main.setTotalQuantity(totalQuantity);
        main.setTotalPrice(totalPrice);
        main.setStatus("DRAFT");
        main.setDeadlineTime(purchaseTime.plusHours(1));  // 1小时后截止
        mainMapper.insert(main);
        for (PurchaseDetail detail : details)
            detail.setPurchaseMainId(main.getId());
        detailMapper.batchInsert(details);
    }
    // 记录限流时间戳
    lastSubmitTime.put(dto.getEmployeeId(), System.currentTimeMillis());
    return Result.success("采购单已生成", orderNo);
}
```

#### 管理员核实与自动截止

　　管理员可对 DRAFT 状态的采购单执行**核实**操作（`PUT /api/purchase/verify/{id}`），将订单提前从 DRAFT 转为 HISTORY 状态。这是管理员人工确认采购完成的入口，不受截止时间限制。

```java
// PurchaseServiceImpl.java - verify()
public Result<Void> verify(Integer orderId, Integer adminId) {
    PurchaseMain main = mainMapper.selectById(orderId);
    if (main == null) throw BusinessException.notFound("采购单");
    if (!main.isDraft())
        throw new BusinessException("只有草稿状态的订单可以核实");
    int rows = mainMapper.verify(orderId);  // UPDATE status='HISTORY'
    if (rows == 0) throw BusinessException.operationFailed("核实失败");
    return Result.success("订单已核实", null);
}
```

　　自动截止则由 Spring `@Scheduled` 注解驱动的定时任务实现，每分钟轮询一次：

```java
// PurchaseScheduler.java
@Scheduled(cron = "0 * * * * ?")  // 每分钟执行
public void autoCompleteDrafts() {
    // 将所有 deadline_time < NOW() 且 status='DRAFT' 的订单 → HISTORY
    // 物理删除过期的 CANCELLED 订单
}
```

　　截止时间从创建时间动态计算（`purchaseTime.plusHours(1)`），替代了固定时间点的方案，使得每张采购单独立拥有 1 小时的有效窗口。

#### 采购弹窗实时计算（前端）

　　采购弹窗采用**事件驱动 + 防抖**的实时计算架构：

- 每个商品行包含数量输入框和折扣百分比（0-100%）输入框
- `@change` 事件触发 200ms 防抖重算，避免高频触发带来的性能问题
- `calcItem()` 为纯函数，执行 `qty × unitPrice × (1 - discount/100)` 公式计算实付金额
- `totalAmount` computed 属性调用 `sum(calcItem(i))` 汇总实付金额
- 汇总区同步显示总数量、折前小计、优惠金额和实付金额

```javascript
// Purchase.vue - 实时计算核心
function calcItem(item) {  // 纯函数，返回实付金额
    const qty = Number(item.quantity) || 0
    const price = Number(item.unitPrice) || 0
    const discount = Math.min(100, Math.max(0, Number(item.discount) || 0))
    return (qty * price * (1 - discount / 100)).toFixed(2)
}

function debouncedRecalc() {  // 200ms 防抖
    clearTimeout(recalcTimer)
    recalcTimer = setTimeout(() => {
        purchaseItems.value.forEach(i => { i.subTotal = calcItem(i) })
    }, 200)
}
```

　　这种架构相较于使用深 `watch` 实现的方式，避免了自我触发问题，同时通过防抖和纯函数确保了计算的可预测性和性能。`onUnmounted` 生命周期中清理 `recalcTimer` 定时器，防止内存泄漏。

### 5.7 逻辑删除唯一性冲突问题与解决

　　在系统开发过程中发现了一个数据库设计层面的 Bug。系统对 supplier、goods、employee、member 四张表采用逻辑删除（is_deleted 标记），但同时这些表的关键字段上有数据库级别的 UNIQUE 约束。当记录被逻辑删除后（is_deleted=1），关键字段值仍保留在表中，导致 UNIQUE 约束依然生效，新记录无法复用该值。

　　具体表现为：用户 A 的手机号为 `13800000000`，被逻辑删除后 `is_deleted=1`，但手机号仍留在表中。新用户 B 注册时系统查询 `selectByPhone`（已过滤 is_deleted=0）认为号码可用，但 MySQL 的 UNIQUE 约束拦截插入，返回 `Duplicate entry` 错误。此外，如果简单地将手机号改为 `del_` 前缀，当两个用户先后被删除时会产生相同的 `del_` 前缀值，导致第二次删除失败。

#### 解决方案：del_{id}_ 前缀

　　采用 `CONCAT('del_', id, '_', 字段值)` 方式，在逻辑删除时将关键字段修改为带唯一标识的前缀。由于 id 是主键，全局唯一，因此确保了 `del_` 前缀后的值永不冲突。四张表的改造如下：

| 表 | 冲突字段 | 唯一约束 | 删除 SQL 改造 |
|---|---|---|---|
| `employee` | `phone` | `uq_employee_phone` | `SET phone = CONCAT('del_', id, '_', phone), is_deleted = 1` |
| `member` | `phone` | `uq_member_phone` | `SET phone = CONCAT('del_', id, '_', phone), is_deleted = 1` |
| `supplier` | `phone` | `uq_supplier_phone` | `SET phone = CONCAT('del_', id, '_', phone), is_deleted = 1` |
| `goods` | `(supplier_id, name)` | `uq_goods_supplier_name` | `SET name = CONCAT('del_', id, '_', name), is_deleted = 1` |

　　改造效果验证：

```
删除 employee#1 (phone=13800000001): → phone 变为 del_1_13800000001，原值 13800000001 释放
新建 employee#2 (phone=13800000001): → 成功，UNIQUE 约束不冲突
删除 employee#2 (phone=13800000001): → phone 变为 del_2_13800000001，不冲突
```

　　该方案仅修改 Mapper XML 中 `deleteById` 的 SQL 语句（4 行改动），不需要修改 Java 代码或数据库 Schema，零侵入、零风险。如需恢复已删除的数据，只需将 `del_{id}_` 前缀去除即可。

### 5.9 Redis缓存优化

　　为提升系统查询性能，减少数据库重复查询压力，系统引入了Redis缓存层。采用Spring Cache抽象（`@Cacheable`/`@CacheEvict`）+ Redis作为缓存存储，对读多写少的单条记录查询进行缓存。

#### 缓存策略

　　系统的缓存策略遵循以下原则：（1）缓存前端实际调用的`search()`分页查询，key为复合参数（搜索条件、筛选、页码、每页数）；（2）写操作（add/update/delete/batchImport/approve/reject）统一使用`allEntries = true`清除该实体全部缓存；（3）不缓存login接口（安全敏感）、采购提交/核实（高频写）；（4）全局TTL设为10分钟，防止缓存雪崩。

#### 缓存覆盖范围

| 缓存名称 | 对应实体 | 缓存方法 | 失效方法 |
|----------|----------|----------|----------|
| `goods` | 商品 | `search`（分页查询） | `add`, `update`, `delete`, `batchImport` |
| `employees` | 员工 | `search`（分页查询） | `register`, `add`, `update`, `delete`, `batchImport`, `approve`, `reject` |
| `members` | 会员 | `search`（分页查询） | `add`, `update`, `delete`, `batchImport` |
| `suppliers` | 供应商 | `search`（分页查询） | `add`, `update`, `delete`, `batchImport` |

#### 实现细节

　　依赖方面，在`pom.xml`中新增了`spring-boot-starter-data-redis`（Redis客户端Lettuce）、`commons-pool2`（连接池）和`spring-boot-starter-cache`（Spring Cache抽象）三个依赖。配置方面，在`application.yml`中配置Redis连接地址（localhost:6379）、连接池参数和全局缓存TTL。

　　序列化方面，自定义了`RedisConfig.java`，配置`RedisTemplate`和`CacheManager`使用Jackson JSON序列化。通过注册`JavaTimeModule`支持`LocalDateTime`类型，启用Jackson默认类型（`DefaultTyping.NON_FINAL`）以支持多态反序列化。

　　启用方面，在`SupermarketApplication.java`上添加`@EnableCaching`注解，零业务代码入侵，仅通过注解声明缓存规则。

## 6. 总结与展望

　　本系统基于Spring Boot + MyBatis后端框架和Vue.js前端框架，成功实现了超市进销存管理系统的核心功能。系统涵盖了供应商管理、商品管理、员工管理、会员管理和采购管理五大管理模块，支持管理员和普通用户两种权限角色，前端的仪表盘导航与路由系统构建了完整的管理界面，能够满足超市日常运营管理的基本需求。

　　在技术实现方面，系统采用了以下关键技术：（1）前后端分离架构，前端通过HTTP协议调用后端RESTful API，实现了表现层与业务逻辑层的解耦；（2）MyBatis持久层框架，通过XML映射文件实现灵活的SQL编写和动态查询；（3）事务管理机制，通过`@Transactional`注解确保采购业务中多表操作的数据一致性；（4）采购单状态机模型，定义了DRAFT→HISTORY/CANCELLED的状态流转规则，支持管理员核实提前提交，截止时间设为创建后1小时，配合@Scheduled每分钟轮询自动截止；（5）三层防重复提交机制，结合前端5秒冷却、后端5秒限流和订单号防重，有效防止重复提交；（6）用户注册与审批机制，用户可自行注册，管理员审核通过后方可登录；（7）采购弹窗实时计算，采用纯函数`calcItem()`+200ms防抖+折扣公式，汇总区同步显示小计/优惠/实付；（8）统一异常处理，通过`@RestControllerAdvice`全局拦截异常并返回规范的JSON响应；（9）数据库CASCADE/RESTRICT外键策略，组合关系级联删除、关联关系限制删除，保证数据完整性；（10）逻辑删除唯一性冲突修复，采用`del_{id}_`前缀策略规避UNIQUE约束冲突；（11）Redis缓存优化，采用Spring Cache抽象+Redis对分页查询结果进行缓存，写操作自动清除全部缓存，有效降低数据库重复查询压力。

　　系统目前仍存在一些可以改进的地方：（1）尚未实现销售管理模块，进销存系统中的"销"和"存"功能有待完善；（2）缺少JWT等基于Token的身份认证机制，当前登录仅返回员工信息，安全性有待提升；（3）缺少数据统计分析和报表功能（如采购趋势图、供应商贡献度分析等）；（4）会员积分自动升级策略尚未实现自动化规则引擎。后续可以在这些方向上进行功能扩展和性能优化。
