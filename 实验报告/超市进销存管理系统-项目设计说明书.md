## 1. 项目概述

### 1.1 项目背景

　　随着零售行业的数字化转型加速，中小型超市对信息化管理的需求日益增长。传统的纸质记录和Excel表格管理方式已无法满足现代超市对供应商、商品、员工、会员和采购业务的一体化管理需求。本项目旨在开发一套功能完善、操作简便的超市进销存管理系统，帮助超市实现日常业务的数字化管理。

### 1.2 项目目标

　　（1）实现供应商、商品、员工、会员基础数据的信息化管理，支持增删改查和批量导入操作。

　　（2）实现采购管理功能，支持采购主表和采购明细表的联动操作，通过事务管理保证数据一致性。

　　（3）实现管理员和普通用户两种权限角色，普通用户只能查看信息，管理员可以进行全部操作。

　　（4）提供规范的RESTful API接口，支持前后端分离架构，便于后续前端开发和系统扩展。

### 1.3 适用范围

　　本系统适用于中小型超市、便利店等零售企业的日常进销存管理。系统采用B/S架构，管理员和员工通过浏览器即可访问系统，无需安装客户端软件。

## 2. 技术架构设计

### 2.1 整体架构

　　系统采用前后端分离的三层B/S架构，整体架构如下图所示：

```
┌─────────────────────────────────────────────────────────────────────┐
│                      前端 (Vue 3 + Element Plus)                     │
│                                                                     │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ │
│  │ 登录页   │ │ 供应商   │ │ 商品管理 │ │ 员工管理 │ │ 会员管理 │ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────┘ │
│                      ┌──────────┐                                   │
│                      │ 采购管理 │ ← 三个Tab: 待处理/已完成/已删除    │
│                      └──────────┘                                   │
│  职责：用户引导 + 防御奇葩操作 + 实时同步 + 5秒冷却                  │
└───────────────────────────────────────┬─────────────────────────────┘
                                        │ HTTP / JSON
┌───────────────────────────────────────┴─────────────────────────────┐
│                    后端 (Spring Boot + MyBatis)                      │
│                                                                     │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐                 │
│  │ Controller  │→│  Service    │→│   Mapper    │→  MySQL          │
│  │ (薄层)      │  │ (业务逻辑)   │  │ (数据访问)  │                 │
│  └─────────────┘  └─────────────┘  └─────────────┘                 │
│                         │                                           │
│                         ├── Fail-fast 校验（参数/业务规则）          │
│                         ├── @Transactional（多表原子操作）           │
│                         ├── 限流（5秒 + 订单号防重复）               │
│                         └── Logger 日志（INFO/WARN/ERROR）          │
│                                                                     │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │                     定时任务 @Scheduled                       │    │
│  │              每分钟轮询 → DRAFT→HISTORY                      │    │
│  │              清理过期 CANCELLED 订单                          │    │
│  └─────────────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────────────┘

**各层职责**：

- **前端表现层（Vue 3 + Element Plus）**：负责用户界面展示和交互。前端核心职责是引导用户正确操作、防御奇葩输入（数字 min/max 限制、5秒冷却按钮）、不静默处理错误（后端返回的错误直接显示，不截断）。
- **后端业务逻辑层（Spring Boot）**：Controller 保持薄层，仅做路由转发。Service 层承载全部业务逻辑——遵循 Fail-fast 原则（参数和业务规则不合规第一时间抛异常）、不信任前端（价格、状态从数据库取，不从前端传）、通过 @Transactional 保证多表操作原子性、通过限流机制防止重复提交。
- **数据访问层（MyBatis）**：通过 Mapper 接口 + XML 映射文件完成数据库操作，支持动态 SQL 和批量操作。

### 3.2 管理员模块

#### 3.2.1 供应商管理

**功能描述**：管理员可以对供应商信息进行完整的增删改查和批量导入操作。

**业务规则**：
- 供应商名称不能为空，长度不超过100字符。
- 供应商电话不能为空，格式为7-20位数字或连字符。
- 电话在系统中必须唯一。
- 邮箱如果填写，必须符合邮箱格式。
- 删除供应商前检查是否有关联商品，有商品则提示先处理商品。
- 使用逻辑删除（is_deleted=1），保留历史数据。

**批量导入**：支持一次性导入多条，批量校验数据格式和电话唯一性，使用`@Transactional`保证原子性。

#### 3.2.2 商品管理

**功能描述**：管理员可以对商品信息进行完整的增删改查和批量导入操作。

**业务规则**：
- 商品名称不能为空，长度不超过100字符。
- 商品单价不能为空且不能为负数。
- 必须指定供应商，系统校验供应商是否存在。
- 同一供应商下商品名称唯一。
- 删除商品前检查是否有采购记录引用，有则阻止删除。
- 查询时自动 LEFT JOIN 关联供应商名称。

#### 3.2.3 员工管理

**功能描述**：管理员可以对员工信息进行完整的增删改查和批量导入操作。系统采用**用户注册+管理员审批**机制，用户可在登录页自行注册，管理员审批通过后方可登录。

**业务规则**：
- 新增员工默认密码为"123456"，使用SHA-256加密存储。
- 员工级别：1-普通员工，2-管理员。
- 手机号在系统中唯一。
- 用户注册后`is_approved=0`为待审批状态，管理员审批通过后`is_approved=1`方可登录。
- 登录时检查`is_approved`状态，未审批返回"您的账号正在等待管理员审批"。
- 管理员直接新增的员工自动设为`is_approved=1`。
- API返回员工信息时自动清除密码字段（设为null），防止密码泄露。
- 删除员工前检查是否有关联采购记录。
- 使用逻辑删除（is_deleted=1），标记为离职状态。

#### 3.2.4 会员管理

**功能描述**：管理员可以对会员信息进行完整的增删改查和批量导入操作。

**业务规则**：
- 会员电话唯一。
- 新增会员默认积分为0，默认等级为1（普通会员）。
- 如果没有指定注册时间，自动设为当前时间。
- 会员等级：1-普通、2-银卡、3-金卡、4-钻石。

#### 3.2.5 采购管理

**功能描述**：采购管理是系统的核心业务模块。前端呈现三个Tab页面——**待处理**（DRAFT状态）、**已完成**（HISTORY状态）、**已删除**（CANCELLED状态）。管理员可以创建采购单、添加采购明细、修改草稿状态的采购单、作废采购单。管理员可执行**核实**操作将DRAFT提前转为HISTORY。系统每分钟轮询一次，自动将超过截止时间（创建后1小时）的DRAFT转为HISTORY。

**业务规则**：
- 采购清单号由后端生成，格式为"PO-YYYYMMDD-XXX"（XXX为当日5位序号）。
- 价格从数据库 Goods 表获取，不信任前端传参。
- 自动计算总数量和总金额。
- 只有"草稿（DRAFT）"状态的采购单可以被修改和作废。
- 每个员工每天只能有一个 DRAFT 采购单——再次提交时 UPDATE 而非 INSERT。
- 新增和修改操作使用事务管理，确保主表和明细表数据一致性。
- 管理员可执行**核实**操作（DRAFT→HISTORY），提前将采购单提交。
- 采购单**截止时间为创建后1小时**，由调度器每分钟轮询自动提交过期订单。
- 删除采购单时先删明细再删主表（或依赖 CASCADE 外键）。

**采购单状态机详见** [6.1 采购模块状态机](#61-采购模块状态机)。

### 3.3 普通用户模块

**功能描述**：普通员工登录后可以查看自己的信息和公共数据，仅提供只读查询功能。

**功能列表**：
- 查看自己的员工信息（姓名、电话、级别、工资等）。
- 分页查询所有商品信息（含供应商名称）。
- 查看单个商品详情。
- 分页查询所有采购单信息。
- 查看采购单详情（含采购明细）。

## 4. 数据库设计

### 4.1 数据库选型

　　选用MySQL 8.0作为数据库管理系统，理由如下：
- 开源免费，社区活跃，文档完善。
- 支持InnoDB存储引擎，提供完整的事务支持（ACID特性）。
- 支持外键约束，保证数据引用的完整性。
- 性能稳定，适合中小型应用的数据存储需求。
- 与Spring Boot + MyBatis技术栈高度兼容。

### 4.2 E-R图与删除策略

　　系统的实体关系（E-R）图及外键删除策略如下：

```

│ supplier │       │ employee │       │     member     │
│ (供应商) │       │ (员工)   │       │    (会员)      │
└────┬─────┘       └────┬─────┘       └────────────────┘
     │                   │
     │ RESTRICT          │ RESTRICT
     ▼                   ▼
┌──────────┐       ┌────────────────┐
│  goods   │       │ purchase_main  │
│ (商品)   │       │   (采购主表)    │
└────┬─────┘       └───────┬────────┘
     │                     │
     │ RESTRICT            │ CASCADE
     │                     │
     └──────────┬──────────┘
                ▼
         ┌────────────────┐
         │purchase_detail │
         │  (采购明细)     │
         └────────────────┘
```

**删除策略总结**：

| 策略 | 适用场景 | 说明 |
|------|----------|------|
| **CASCADE** | 采购主表 → 采购明细 | 组合关系，明细不能脱离主表独立存在，同生共死 |
| **RESTRICT** | 供应商 → 商品、员工 → 采购主表、商品 → 采购明细 | 关联关系，有业务引用时阻止删除，保护历史数据完整性 |

### 4.3 六张表概览

| 表名 | 主键 | 逻辑删除 | 关键外键 |
|------|------|----------|----------|
| supplier | id | is_deleted | - |
| goods | id | is_deleted | supplier_id → supplier (RESTRICT) |
| employee | id | is_deleted | - |
| member | id | is_deleted | - |
| purchase_main | id | ❌（物理保留） | employee_id → employee (RESTRICT) |
| purchase_detail | id | ❌ | purchase_main_id → purchase_main (CASCADE), goods_id → goods (RESTRICT) |

**设计说明**：
- 基础数据表（supplier、goods、employee、member）使用逻辑删除（is_deleted=1），防止数据误删后无法恢复。
- 采购业务表（purchase_main、purchase_detail）使用物理删除，因为采购数据作为业务流水记录，通过状态机（DRAFT/HISTORY/CANCELLED）管理生命周期。

## 6. 核心业务设计

### 6.1 采购模块状态机

　　采购单的生命周期由状态机管理，三种状态之间的转换规则如下：

```
                     用户提交采购
                          ↓
                    ┌─────────────┐
                    │    DRAFT    │  ← 可修改、核实、作废
                    │   (草稿)     │
                    └──────┬──────┘
                           │
             ┌─────────────┼─────────────┐
             │             │             │
          用户修改       用户作废    管理员核实 /
          重新提交          │        1小时后自动
             │             │        (@Scheduled)
             ▼             ▼             ▼
       回到 DRAFT    ┌──────────┐  ┌──────────┐
                     │CANCELLED │  │ HISTORY  │
                     │ (已作废)  │  │ (只读)    │
                     └────┬─────┘  └──────────┘
                          │              │
                    截止前可恢复     不可修改删除
                    截止后物理删除   已通知供应商
```

**状态说明**：

| 状态 | 含义 | 可操作 | 说明 |
|------|------|--------|------|
| DRAFT | 草稿 | 修改、作废、核实 | 每个员工每天只有一个DRAFT，再次提交是UPDATE |
| HISTORY | 已截止 | 仅查看 | 由管理员核实或1小时后自动转换，已通知供应商 |
| CANCELLED | 已作废 | 截止前可恢复为DRAFT | 截止后由定时任务物理删除 |

### 6.2 三层防重复机制

　　为防止用户重复提交采购单，系统设计了三层防线：

```
用户操作                        防线                          存储
──────                        ──────                        ────

点"提交采购"
    ↓
弹窗 + 5秒冷却              【第1层：前端防抖】             组件状态
按钮变灰，倒计时              挡住：手抖连点
    ↓ 5秒后点确定
发送请求
    ↓
后端收到
    ↓
检查员工30秒内是否提交       【第2层：后端限流】             ConcurrentHashMap
    ├─ 是 → 429              挡住：F5刷新后重提交           employeeId → lastTime
    └─ 否 → 继续
    ↓
检查订单号是否已使用          【第3层：订单号防重】          ConcurrentHashMap
    ├─ 是 → 拒绝             挡住：多标签页绕开             orderNo → used
    └─ 否 → 继续
    ↓
执行业务
```

**实现要点**：

- **第1层（前端）**：点击"创建采购单"打开弹窗，提交成功后弹窗关闭，按钮变灰显示5秒倒计时。冷却期间点击无反应。
- **第2层（后端）**：使用 `ConcurrentHashMap<employeeId, lastSubmitTime>` 记录每个员工最近一次提交时间。如果距上次提交不足5秒，返回 HTTP 429。
- **第3层（后端）**：使用 `ConcurrentHashMap<orderNo, used>` 标记已使用的订单号。前端先通过 `GET /api/purchase/order-no` 获取预订单号（后端标记为"已分配"），提交时校验该订单号未被使用过。

### 6.4 定时任务设计

　　系统使用 Spring `@Scheduled` 注解实现定时任务，核心任务如下：

**任务：DRAFT → HISTORY（每分钟轮询）**

```java
@Scheduled(cron = "0 * * * * ?")  // 每分钟执行
@Transactional(rollbackFor = Exception.class)
public void deadlineTask() {
    LocalDateTime now = LocalDateTime.now();

    // 1. 查询所有 status=DRAFT 且 deadline_time<=NOW()
    List<PurchaseMain> expiredDrafts = mainMapper.selectExpiredDrafts(now);
    if (!expiredDrafts.isEmpty()) {
        List<Integer> ids = expiredDrafts.stream().map(PurchaseMain::getId).collect(Collectors.toList());
        mainMapper.batchUpdateToHistory(ids);
        log.info("[Deadline锁定] 共锁定{}笔订单", ids.size());
    }

    // 2. 物理删除过期的CANCELLED订单
    int deleted = mainMapper.deleteCancelledExpired(now);
    if (deleted > 0) {
        log.info("[Deadline清理] 共删除{}笔过期作废订单", deleted);
    }
}
```

**Cron 表达式说明**：`0 * * * * ?` = 每分钟执行（轮询过期DRAFT订单）

### 6.5 事务管理设计

　　采购模块的增删改操作都涉及多张表的数据库操作，必须使用事务管理保证数据一致性。

**事务边界**：

| 操作 | 事务范围 | 回滚条件 |
|------|----------|----------|
| 提交采购单 | insert or update(main) + deleteDetails + batchInsert(details) | 任一步失败即全部回滚 |
| 作废采购单 | updateStatus(main) | 更新失败即回滚 |
| 物理删除 | deleteDetails + delete(main) | 任一步失败即全部回滚 |
| 定时任务 | updateStatus ALL + cleanExpired | 任一步失败即全部回滚 |
| 批量导入 | batchInsert(items) | 插入失败即全部回滚 |

**事务实现方式**：

通过Spring的声明式事务管理，在Service层方法上添加`@Transactional(rollbackFor = Exception.class)`注解。当方法执行过程中抛出任何异常，Spring会自动回滚该事务中的所有数据库操作。

```java
@Transactional(rollbackFor = Exception.class)
public PurchaseMain submitPurchase(PurchaseMain main, List<PurchaseDetail> details) {
    // 1. 从goods表取单价（不信任前端）
    // 2. 计算 totalQuantity、totalPrice
    // 3. 检查今天是否已有DRAFT → 有则UPDATE，无则INSERT
    // 4. 删除旧明细 + 插入新明细
    // 所有操作在同一事务中，任何异常都会触发回滚
}
```

**事务隔离级别**：使用MySQL InnoDB默认的REPEATABLE READ隔离级别。

### 6.6 异常处理设计

　　系统采用统一的异常处理机制，通过`@RestControllerAdvice`全局拦截异常并返回规范的JSON响应。

**异常层次结构**：

```
Exception（所有异常）
├── BusinessException（业务异常，code + message）
│   ├── paramError("...")     → code=400
│   ├── notFound("...")       → code=404
│   ├── duplicate("...")      → code=409
│   ├── unauthorized("...")   → code=401
│   └── operationFailed("...")→ code=500
│
├── BindException（参数校验异常）→ code=400
│
├── TransactionSystemException（事务异常）→ code=500
│
└── Exception（其他未知异常）→ code=500
```

**GlobalExceptionHandler实现**：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public Result<?> handleBusinessException(BusinessException e) {
        log.warn("[业务异常] code={}, message={}", e.getCode(), e.getMessage());
        return Result.error(e.getCode(), e.getMessage());
    }

    @ExceptionHandler(BindException.class)
    public Result<?> handleBindException(BindException e) {
        String message = e.getBindingResult().getAllErrors().get(0).getDefaultMessage();
        return Result.paramError(message);
    }

    @ExceptionHandler(TransactionSystemException.class)
    public Result<?> handleTransactionException(TransactionSystemException e) {
        log.error("[事务回滚] 事务执行失败，已回滚", e);
        return Result.error(500, "操作失败，数据已回滚，请重试");
    }

    @ExceptionHandler(Exception.class)
    public Result<?> handleException(Exception e) {
        log.error("[系统异常] 未知错误", e);
        return Result.systemError();
    }
}
```

### 6.7 数据校验设计

　　系统采用多层校验机制，确保数据完整性：

| 层次 | 位置 | 职责 | 失败处理 |
|------|------|------|----------|
| **第1层** | 前端（Vue 3表单验证） | 必填项、长度、格式、数字min/max | 表单提示，阻止提交 |
| **第2层** | Controller（@Valid注解） | `@NotBlank`、`@NotNull`、`@Pattern`等 | BindException → 400 |
| **第3层** | Service（Fail-fast校验） | 唯一性检查、外键存在性检查、限流检查 | BusinessException → 400/429 |
| **第4层** | 数据库约束 | UNIQUE KEY、FOREIGN KEY、NOT NULL | MySQL异常 → 事务回滚 |

**Fail-fast 原则**：所有校验在业务逻辑的最前面执行，不合规第一时间抛异常，绝不带着错误数据继续往下走。

## 9. 安全设计

**密码安全**：
- 员工密码采用SHA-256算法进行单向哈希加密存储，不可逆。
- 登录时将用户输入的密码进行SHA-256加密后与数据库密文比对。
- API返回员工信息时自动将密码字段置为null，防止密码泄露。

**权限控制**：
- 员工的level字段区分权限角色：1为普通员工（只能查看），2为管理员（可进行增删改操作）。
- 管理员接口（/api/supplier、/api/goods、/api/employee、/api/member、/api/purchase）和普通用户接口（/api/user）路径分离。

**数据安全**：
- 基础数据表（supplier、goods、employee、member）使用逻辑删除，防止数据误删后无法恢复。
- 采购明细表记录采购时的商品价格快照（unit_price），即使后续商品价格调整，历史采购记录不受影响。
- 不信任前端传入的价格数据，所有价格从数据库 Goods 表实时获取。

**防重复提交**：
- 三层防重复机制（详见 [6.2](#62-三层防重复机制)）：前端弹窗关闭后5秒冷却 + 后端5秒限流 + 订单号防重。
- 用户注册审批机制：用户自行注册→待管理员审核→审核通过后方可登录。

**前后端分离安全（待实现）**：
- 配置CORS跨域策略，限制允许访问的前端域名。
- 实现JWT Token认证，替代当前的简单参数传递方式。
- 添加请求拦截器，统一校验Token有效性和用户权限。
