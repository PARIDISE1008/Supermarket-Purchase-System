### 1. 逻辑删除 UNIQUE 冲突 Bug 修复

发现所有带 `is_deleted` 的表（supplier、goods、employee、member）存在同一个问题：逻辑删除后关键字段（phone、name）仍保留在表中，数据库 UNIQUE 约束生效，导致新记录无法复用该值。

**根因分析**：
- Service 层 `selectByPhone` 过滤 `is_deleted=0`，认为号码可用
- DB 层 UNIQUE 约束覆盖所有行（含 `is_deleted=1`），拦截 INSERT
- 简单 `del_` 前缀不可行：二次删除时 `del_` 值重复

**方案**：`CONCAT('del_', id, '_', 字段值)` — id 是主键，全局唯一

**改动文件（4 个 Mapper XML，仅改 `deleteById` SQL）**：

| 文件 | 行 | 原 SQL | 新 SQL |
|---|---|---|---|
| `EmployeeMapper.xml` | 75 | `SET is_deleted = 1` | `SET phone = CONCAT('del_', id, '_', phone), is_deleted = 1` |
| `MemberMapper.xml` | 79 | 同上 | 同上模式 |
| `SupplierMapper.xml` | 89 | 同上 | 同上模式 |
| `GoodsMapper.xml` | 80 | 同上 | `SET name = CONCAT('del_', id, '_', name), is_deleted = 1` |

零 Java 改动，零 Schema 改动。

## 技术要点

- MySQL UNIQUE 约束 + 逻辑删除的冲突本质：应用层和数据库层对"已删除"的理解不一致
- `CONCAT` 方案对比其他方案的优势：不入侵 Java 逻辑、不改 Schema、不改查询、支持恢复
- 数据生成时的全场景覆盖：含 NULL 手机号员工（验证 nullable 唯一）、真实商品名（验证中文编码）
