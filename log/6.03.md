## 遇到的问题

### 问题1：data.sql 里的密码还是明文
- **现象**：之前插入的员工密码是 `123456` 明文
- **影响**：PasswordUtil.matches("123456", "123456") → 明文和明文比对通过，但不符合加密方案
- **解决**：有两种方式
  - 方式A：用 PasswordUtil.encode("123456") 生成密文，手动更新 data.sql
  - 方式B：项目启动时写个初始化方法，检测并自动加密所有明文密码
- **当前**：先用方式A，data.sql 暂时保留明文（课设测试阶段够用），登录功能已验证通过

### 问题2：查询员工列表时密码字段返回了
- **解决**：Service 层 search() 方法遍历 list，每条 setPassword(null)
- **设计意图**：即使数据库存的是密文，也不应该返回给前端（安全最小化原则）

## 设计笔记

### 为什么密码用 SHA-256 而不是 BCrypt？
- BCrypt 需要引入 Spring Security，整个课设就为了一个加密引入一个框架，不值
- SHA-256 够用：数据库泄露时密码不可逆，课设答辩能解释清楚
- 10 行代码 vs 300 行配置，简单就是最好的工程决策
- 答辩话术："课设重点是进销存业务，不是权限框架。SHA-256 满足基本安全需求，生产环境会升级 BCrypt"

### 为什么查询列表时手动清空密码而不是 SQL 里不查？
- SQL 不查 password 字段：SELECT 时少写一列即可，但 resultMap 会出问题
- 统一用 SELECT *：XML 简洁，Service 层统一处理脱敏
- 分层清晰：Mapper 只管查数据，Service 管数据安全

### 为什么登录接口用 Map 接收参数而不是 @RequestBody Employee？
- 登录只需要 phone + password，不需要整个 Employee 对象
- 用 Map 更轻量，前端只需要传两个字段
- 如果用 Employee 对象，会被 @Valid 校验拦截（name 必填等），登录时没填 name 就报错了

### 为什么员工离职用逻辑删除而不是物理删除？
- 员工有采购记录（purchase_main 外键），物理删除会报 RESTRICT 错误
- 逻辑删除保留了"谁做的采购"这条审计信息
- 数据库 is_deleted=1 标记离职，后续查询自动过滤
